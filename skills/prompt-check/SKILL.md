# Prompt Check — 项目需求理解与确认

## 一、核心目标

在正式执行任务前，准确理解用户原始 Prompt，结合真实项目代码、文档和约定，形成可验证的需求理解，并交由用户确认。

核心原则：

1. 以用户真实目标为中心，不机械照搬 Prompt。
2. 先探索真实项目，再形成需求判断，不臆测代码现状。
3. 先完成已授权的只读工作，再询问关键问题。
4. 只对可能改变实现方向或验收结果的不确定项提问。
5. 用户确认前严格只读，确认后按授权范围执行。
6. 用户明确指令优先于本 Skill 的默认流程；不得违反更高优先级的指令。

## 二、执行流程

### 1. 分析原始 Prompt

分析用户输入，提取：

- 任务类型：开发、修复、重构、审查、优化等。
- 用户明确提出的目标和预期结果。
- 隐含需求及其成立条件。
- 功能范围、技术约束和禁止事项。
- 用户期望的交付物及验收标准。

区分明确要求、合理推断和未知信息，不把推断当作事实。

### 2. 先探索项目，再形成理解

必须先使用可用的只读工具探索与任务直接相关的真实项目上下文。

优先检查：

- 项目入口、目录结构及相关模块。
- 现有功能实现、调用关系和数据流。
- 相关测试及测试约定。
- README、项目文档、AGENTS.md 和适用的项目规则。
- 可能影响本次任务的现有设计和技术约束。
- Git 当前状态及相关未提交变更（工具可用时）。

要求：

- 通过 read / grep / glob 等实际可用工具获取证据。
- 根据需求逐步扩大检索范围，不进行无关的全库通读。
- 记录相关文件路径、关键实现和必要的代码位置。
- 不臆测不存在的文件、接口、函数或业务行为。
- 不读取与任务无关的敏感配置、密钥和凭证。
- 如果无法访问项目，明确说明未能核实的部分。

### 3. 确认前的执行边界

用户确认前，本阶段只负责需求理解。

禁止：

- 修改、创建、删除项目文件。
- 安装依赖、构建项目、运行测试。
- 执行 Git 写操作或其他有副作用的命令。
- 调用任何写入类工具。
- 输出代码、补丁或具体实施方案。

允许：

- 读取代码、文档和测试。
- 搜索、检索和分析项目。
- 梳理需求、约束、风险和验收标准。
- 提出必要的澄清问题。

### 4. 识别不确定项并主动提问

完成项目探索后，判断是否存在真正需要用户决策的信息。

按以下规则处理：

- 能从用户 Prompt、项目文档或代码确定的，不提问。
- 能依据项目现有约定合理推断且不会影响结果的，直接采用，并在必要时标注假设。
- 只有可能影响功能行为、架构设计、接口兼容性、数据处理、用户体验、任务范围或验收结果的信息，才列为待确认项。
- 涉及不可逆操作、外部写入或重大范围变更时，明确确认授权边界。

提问要求：

1. 尽可能一次性提出所有必要问题，避免多轮零散追问。
2. 每个问题采用「问题 + 2-4 个选项 + 简洁说明」的形式，适当给出推荐选项，位于前列。
3. 选项应真实反映可行选择，不强行制造选项。
4. 允许用户自定义回答。
5. 问题数量不设固定上限，但以消除真正的阻塞项为准，不为了追求全面而过度提问。
6. 优先使用当前环境实际提供的 ask 工具；没有该工具时直接向用户提问。

如果不存在影响任务执行的关键不确定项，不必人为制造问题，直接进入用户确认环节。

### 5. 输出需求理解报告

严格使用以下结构：

## 已核实的项目现状

使用表格展示相关文件、实际发现及其与本次需求的关系。

只列出足以证明已经理解相关项目上下文的文件，不罗列无关文件。

没有实际证据的内容必须标记为未核实。

## 重新复述用户 Prompt

使用自己的话重新描述用户原始需求。

要求：
- 准确保留用户的真实意图。
- 消除歧义、重复和模糊表达。
- 不擅自增加用户没有要求的功能。
- 不输出内部推理过程。

## 试图解决的问题与用户目标

明确以下内容：

| 维度     | 需要明确的内容                     |
| -------- | ---------------------------------- |
| 使用对象 | 项目或功能给谁使用                 |
| 目标     | 需要解决什么问题，最终达到什么效果 |
| 范围     | 本次需要做什么，不涉及什么         |
| 约束     | 技术、兼容性、性能、项目规范等限制 |
| 验收     | 通过什么事实、行为或测试判定完成   |

区分用户明确要求和根据项目现状推断的内容。

## 不确定之处

列出确实需要用户决策的问题及其原因。

如果没有，明确写明：目前没有影响执行方向的关键不确定项。

## 一句话概括

30 字以内，准确概括确认后准备执行的任务。

### 6. 用户确认

将完整需求理解报告交给用户确认。

优先使用可用的 ask 工具；否则直接询问。

确认选项：

| 选项           | 行为                               |
| -------------- | ---------------------------------- |
| 确认，开始执行 | 按已确认的需求和范围开始工作       |
| 补充或修改     | 接收补充信息，重新分析受影响的需求 |
| 取消           | 结束本次任务                       |

用户也可以直接输入「开工」「开始」「意图正确」等明确指令。

用户未明确确认前，不得进入写入和实施阶段。

如果用户明确要求跳过本 Skill 的确认流程，则遵循用户本次明确指令。

### 7. 确认后开始工作

用户确认后：

1. 将用户原始 Prompt 和确认后的需求作为执行依据。
2. 按用户要求的任务类型执行，不擅自把审查、分析或规划任务转变为代码修改任务。
3. 遵循项目现有架构、编码规范和技术约定。
4. 在已授权范围内自主完成必要的本地工作，不对已授权的常规、可逆操作重复索取许可。
5. 遇到新的重大不确定项、破坏性操作、外部写入或超出原范围的工作时，先取得必要授权。
6. 根据实际改动执行有针对性的测试和验证，不进行与改动无关的重复测试。
7. 最终报告实际完成内容、修改文件、验证结果及尚未解决的问题。

不得把计划完成、尝试执行或未经验证的结果描述为已经完成。

## 三、执行质量要求

- **真实性**：所有项目现状必须有实际代码或文档依据。
- **完整性**：目标、对象、范围、约束、验收标准必须清晰。
- **准确性**：不把模型推断当作用户确认的需求。
- **效率**：先探索后提问，减少不必要的沟通轮次。
- **自主性**：确认前自主完成必要的只读工作，确认后自主完成已授权任务。
- **边界性**：严格区分需求分析阶段和实际执行阶段。
- **可验证性**：所有最终完成情况均应有对应证据。
