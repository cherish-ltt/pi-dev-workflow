# Project Audit — 全面项目审查

## 一、核心目标与执行边界

全面审查项目，发现并验证：
- 功能 Bug 和业务逻辑缺陷。
- 安全漏洞及权限问题。
- 并发、稳定性及可靠性问题。
- 性能瓶颈及资源浪费。
- 用户体验和交互缺陷。
- 工程质量、架构及维护性问题。

最终交付：**经过验证的问题报告，以及逐项创建的 Git Issue。**

执行原则：
1. 优先自主完成已经明确授权的工作，不要停留在计划或建议阶段。
2. 用户明确指令优先于本 Skill 的默认规则。
3. 先探索真实代码和项目约定，再形成判断。
4. 通过实际测试验证问题，不能只依赖静态分析。
5. 不修改、修复或重构项目正式代码。
6. 不编造问题、测试结果及 Issue 提交状态。
7. 只在关键信息无法推断、可能改变执行方向，或操作超出授权范围时询问用户。

**允许自主执行：** 读取文件、Git 状态检查、代码分析、日志分析、非破坏性本地测试、临时测试代码、隔离环境验证。

**需要额外授权：** 生产环境操作、破坏性测试、不可逆操作、未经授权的外部写入及明显超出原始任务范围的操作。

如果用户已经明确授权某项操作，不得重复请求许可。

## 二、项目探索与环境准备

审查前先了解项目真实情况。

### 1. 项目探索

使用可用的文件读取、搜索、终端及代码分析工具，检查：

- 项目目录、技术栈及入口文件。
- 核心模块、调用链及业务流程。
- README、AGENTS.md、架构文档及开发规范。
- 现有测试、测试覆盖及执行方式。
- 构建、部署和 CI/CD 配置。
- 环境变量、配置文件及外部服务依赖。
- 数据库结构、迁移及数据访问逻辑。
- 第三方依赖及版本兼容性。

要求：
- 优先探索核心路径及高风险模块。
- 不做与审查无关的全库通读。
- 不臆测接口、文件路径及既有行为。
- 记录重要代码位置及证据。
- 项目文档、代码和测试之间存在冲突时，查明实际行为并记录差异。

### 2. Git 环境与远端同步

检查：
- 当前仓库、分支及 Commit SHA。
- 工作区是否干净。
- Git Remote 和上游分支。
- 对应 Git 托管平台。
- 现有 Issue 及项目标签规范。

执行一次安全的远端更新：

- 工作区干净、上游分支明确且可以快进时，执行一次 `git pull --ff-only`。
- 存在未提交修改、分支分叉或冲突风险时，不得强制覆盖、重置或清理用户修改。
- 无法确定远端或上游分支时，不得自行猜测。
- 记录同步前后的 Commit SHA。
- 如果同步受阻，可以继续审查当前代码，但必须说明审查基于哪个版本。

### 3. Issue 平台准备

根据仓库 Remote 和项目配置，识别实际使用的 Git 平台及其 Issue 系统。

确认：
- 对应连接器、插件或 CLI 是否可用。
- 是否具有仓库读取和 Issue 创建权限。
- Issue 模板、标签及分类规范。
- 已有 Issue，避免重复报告。

不得假设项目一定使用某个特定 Git 平台。

如果无法提交 Issue，继续完成审查，生成完整的 Issue 草稿并报告阻碍原因。

## 三、审查策略与并行执行

### 1. 建立审查矩阵

根据项目实际情况建立模块与风险清单。

优先检查：
- 核心业务链路。
- 身份认证及权限边界。
- 数据读写及一致性。
- 并发、异步任务及状态管理。
- 网络通信及外部服务调用。
- 异常处理、超时和重试。
- 配置、部署及环境差异。

再覆盖其他适用领域。

不要机械执行与项目无关的检查项。

### 2. 并行审查

如果具备 Subagent / 多 Agent 工具，且可以提升审查效率或质量，应合理拆分独立任务并行执行。

例如：

| Agent   | 负责领域                 |
| ------- | ------------------------ |
| Agent A | 核心业务逻辑及功能正确性 |
| Agent B | 安全及权限               |
| Agent C | 并发、稳定性及可靠性     |
| Agent D | 性能及资源使用           |
| Agent E | 测试、工程质量及用户体验 |

执行要求：
- 每个 Agent 明确审查范围、限制及输出要求。
- 优先分配互相独立的模块。
- 不同 Agent 不得重复审查相同范围而没有明确理由。
- 所有 Agent 均禁止修改正式代码。
- Agent 返回问题时必须提供文件位置、证据及验证结果。
- 由主 Agent 统一复核、去重、验证和提交 Issue。

如果没有可用的 Subagent，直接顺序审查，不得假设具备多 Agent 能力。

## 四、全面审查领域

### 1. 功能正确性
- 核心业务流程及业务规则。
- 边界条件、异常输入、空值及极端数据。
- 状态转换及条件判断。
- 数据读写、更新、删除及一致性。
- 错误处理、异常传播及遗漏场景。

### 2. 安全性
- 身份认证及权限校验。
- 输入验证、注入及信任边界。
- 敏感信息、密钥及隐私保护。
- 文件、网络及外部接口安全。
- 第三方依赖及不安全配置。

### 3. 稳定性与可靠性
- 超时、重试、取消及失败恢复。
- 并发竞争、死锁及数据竞争。
- 资源泄漏及生命周期管理。
- 网络异常和外部服务不可用。
- 长时间运行及异常状态恢复。

### 4. 性能与资源
- 不必要的计算及重复操作。
- CPU、内存、磁盘和网络资源。
- 数据库查询及缓存策略。
- 并发处理和资源竞争。
- 大数据量及高负载场景。

### 5. 用户体验
- 操作流程及交互一致性。
- 错误提示及异常反馈。
- 加载、等待及操作状态。
- 异常情况下的恢复能力。
- 界面布局、功能可用性及易用性。

### 6. 工程质量
- 模块职责及依赖关系。
- 配置管理及环境兼容性。
- 构建、部署及升级流程。
- 日志、监控及可观测性。
- 测试完整性及文档准确性。
- 第三方依赖及版本兼容性。

根据项目特征扩展必要的审查领域。

## 五、问题验证与测试策略

**禁止仅凭静态代码分析就认定存在 Bug。**

对每个疑似问题，尽可能执行：

1. 定位具体代码及完整调用链。
2. 确认当前实现和预期行为。
3. 分析触发条件及影响范围。
4. 查找已有测试及相关历史问题。
5. 构造最小复现条件。
6. 编写临时测试代码或独立测试脚本。
7. 实际运行并观察结果。
8. 判断问题是否真实存在。

### 1. 测试策略

优先使用现有测试设施：

- 单元测试。
- 集成测试。
- 端到端测试。
- 静态分析及 Lint。
- 类型检查。
- 安全扫描。
- 性能测试及压力测试。
- 故障注入及异常场景测试。

根据风险和问题类型选择必要的测试。

不要为了追求测试数量而重复运行已经通过且没有新风险的测试。

出现测试失败、新发现问题或尚未解决的风险时，再扩大验证范围。

### 2. 临时测试

允许：
- 编写临时测试代码。
- 创建临时测试数据。
- 使用隔离数据库或测试环境。
- 启动本地服务。
- 编写独立复现脚本。
- 使用压测和故障注入工具。

禁止：
- 修改正式业务代码。
- 修改正式测试代码。
- 修改项目配置或依赖版本。
- 覆盖用户已有文件。
- 对生产环境执行破坏性测试。
- 未经授权访问或修改外部数据。

临时文件应放在临时目录或隔离环境，结束后清理。

如果依赖缺失，不得擅自安装或升级，记录无法验证的原因。

### 3. 问题可信度分级

| 状态       | 判断标准                                           | 处理                   |
| ---------- | -------------------------------------------------- | ---------------------- |
| 已复现     | 实际运行能够稳定触发                               | 可以提交               |
| 确定性确认 | 有充分、可复核的代码或数据流证据，但不适合实际触发 | 可以提交，说明验证方式 |
| 待验证     | 有一定线索，但证据不足                             | 暂不提交               |
| 已排除     | 经过验证，问题不存在                               | 不提交                 |

对于安全问题，如果实际利用可能造成数据损坏或其他风险，不得为了复现而进行破坏性操作。可以使用隔离环境或确定性证据确认。

体验改进必须具备明确的用户场景、当前问题及改善价值，不能把个人偏好包装成缺陷。

## 六、Issue 管理与提交

对每一个确认的问题，独立创建一条 Issue。

### 1. 创建前检查

- 搜索现有 Issue。
- 检查是否已有相同问题。
- 检查是否存在关联 Issue。
- 确认问题具有独立的修复价值。

同一根因引起的多个表现可以合并为一条 Issue；不同根因必须分别提交。

如果已有未解决的相同 Issue，引用即可，不重复创建。

如果已有已关闭的相同 Issue，先判断是否为回归或原修复无效，不得直接重复创建或擅自重新打开。

### 2. Issue 标题

使用简洁、明确的标题：

- [Bug] 并发请求下出现数据不一致
- [Security] 用户可以访问未授权资源
- [Performance] 大数据量下查询响应异常
- [Enhancement] 操作失败时缺少明确反馈

遵循项目原有分类及标签规范。

### 3. Issue 正文

每条 Issue 必须包含：

**问题简述**

描述问题是什么，以及发生在什么场景。

**影响范围**

说明影响哪些用户、模块、功能及业务流程。

**复现方式**

- 前置条件。
- 最小复现步骤。
- 必要的命令、测试代码或请求示例。
- 实际运行结果及证据。

**预期行为与实际行为**

明确说明预期结果与实际结果之间的差异。

**修复/改进建议**

提供具体、可执行的改进方向。根因不确定时必须明确标记为推测。

**回归测试建议**

说明修复后应该增加哪些测试，以及需要覆盖的边界条件。

**验收标准**

提供明确、可验证的完成条件。

**环境及证据**

提供版本、Commit SHA、运行环境、日志及测试结果。

不得泄露密钥、Token、密码及用户隐私。

### 4. 优先级

| 优先级 | 定义                                       |
| ------ | ------------------------------------------ |
| P0     | 严重安全漏洞、核心服务不可用、重大数据损坏 |
| P1     | 核心功能严重异常、大范围用户受影响         |
| P2     | 一般功能缺陷、特定条件下出现明显问题       |
| P3     | 轻微缺陷、低影响体验问题                   |

根据实际影响确定优先级，不得夸大。

### 5. 署名与提交

署名必须由用户提供或确认。

格式：

`署名：{用户确认的文本}`

如果用户尚未提供署名：
- 不得自行使用模型名称或其他身份。
- 不要因此停止已经可以完成的审查和测试。
- 在 Issue 提交前询问署名。
- 用户确认后统一用于所有 Issue。

提交要求：
- 使用项目对应的 Git 平台。
- 遵循项目 Issue 模板。
- 每个独立问题单独提交。
- 只提交符合可信度要求的问题。
- 确认平台实际返回的创建结果。
- 保存 Issue 标题、编号及 URL。

对于需要保密的安全漏洞，优先使用平台的私密漏洞报告渠道，不得将敏感漏洞利用细节直接公开到公共 Issue。

如果提交失败，保留完整 Issue 草稿并说明失败原因，不得虚报成功。

## 七、严格禁止事项

1. 修改、修复或重构正式项目代码。
2. 擅自升级依赖或改变项目配置。
3. 为通过测试而修改正式代码或测试。
4. 将未经验证的猜测当作真实 Bug。
5. 提交缺少证据及验收标准的低质量 Issue。
6. 重复创建已有问题的 Issue。
7. 忽略项目文档、业务规则及现有实现。
8. 覆盖用户已有修改或破坏现有环境。
9. 虚构测试结果、复现结果及 Issue 提交状态。
10. 为追求 Issue 数量而制造问题。
11. 无意义地重复测试或无限扩大审查范围。

## 八、最终报告与验收

审查完成后输出报告。

### 1. 审查概况

- 项目及审查范围。
- 审查前后 Commit SHA。
- 涉及模块及关键文件。
- 执行的测试和验证方式。
- 测试通过、失败及无法执行的情况。

### 2. 问题统计

| 优先级 | 数量 |
| ------ | ---: |
| P0     |    N |
| P1     |    N |
| P2     |    N |
| P3     |    N |
| 合计   |    N |

另外区分：
- 功能 Bug。
- 安全问题。
- 性能问题。
- 稳定性问题。
- 体验改进。

### 3. 已提交 Issue

逐项列出：
- Issue 标题。
- 类型及优先级。
- 一句话描述。
- Issue 编号及链接。

### 4. 待验证问题

列出有一定线索但证据不足的问题，并说明：
- 当前证据。
- 无法确认的原因。
- 还需要什么条件才能验证。

不得计入已确认问题统计。

### 5. 审查限制

说明未覆盖模块、无法执行的测试、环境限制及其他风险。

### 6. 最终验收

- [ ] 已探索真实项目代码及相关文档。
- [ ] 已覆盖项目适用的核心审查领域。
- [ ] 已根据风险选择适当的测试方式。
- [ ] 已尽可能通过实际运行验证疑似问题。
- [ ] 已排除重复及缺乏证据的问题。
- [ ] 每个独立确认的问题均创建了 Issue。
- [ ] 每条 Issue 均包含复现证据、改进建议、回归测试及验收标准。
- [ ] 每条 Issue 均使用用户确认的署名。
- [ ] 所有临时测试文件均已清理。
- [ ] 未修改或修复正式项目代码。
- [ ] 已如实报告测试结果、提交结果及审查限制。

**最终原则：以真实证据为依据，以实际验证为标准，以高质量 Issue 为交付物。宁可少提交，也不制造误报。**
